# Service boundaries and future service split

Status: architecture guidance, 2026-10-15. Evidence is from `feature/connected-crm` at commit 712d321. Line references will drift; the rules below do not.

## Summary

The connected CRM is a **modular monolith**: one Rust/Axum crate (`services/crm-api`), one PostgreSQL database with one migration sequence, and one frontend data layer (`src/services/crm/`) that reaches the API only through same-origin `/api/crm/...` paths. The retained Google Calendar companion (`backend/`) is already a separate deployable on `/api/calendar`, and the Vite proxy routes the two prefixes to different processes (`vite.config.js`).

Splitting into microservices now is not recommended. The domains share invariants that PostgreSQL enforces inside one transaction: the per-workspace lock, live-membership checks, redacted activity committed with every mutation, and same-workspace links between records. A split would replace these with distributed coordination before any traffic, team or reliability need exists. The aim is to keep a later split cheap: every table has one owner, modules talk through functions rather than each other's tables, and new large features are built as separately owned modules.

## When a split is justified

Extract a domain only when at least one of these signals is measured or decided, and record it in the decision log below:

- **Different exposure:** anonymous, internet-facing endpoints (public website, enquiry intake, guest agreement links, provider webhooks) that should not share a process, credentials or connection pool with private CRM data.
- **Independent scale:** for example, public catalogue reads dominating load and needing caches or replicas the CRM does not.
- **Failure isolation:** slow or failing external providers (email, WhatsApp, social, AI) must not hold CRM requests or database connections.
- **Independent ownership or release cadence:** separate teams repeatedly blocked by one deploy.
- **Compliance or evidence requirements:** separate keys, retention or storage, for example for the agreement evidence store.
- **Measured database contention** that indexing, pagination or a read replica cannot fix.

File counts, "best practice" and a wish for separate repositories are not reasons.

Strengths to keep:

- One API prefix, with one client file per domain in `src/services/crm/`.
- The finance pattern: its own router merged with one line, its own error-code range and its own history table.
- `workspace_id` on every row and UUID server IDs.
- One `{message, code}` error shape.
- The separate Calendar companion.

## Boundary rules (apply from now on)

1. **One owner per table.** Every table belongs to exactly one module in the domain map. New migrations state the owner in their header comment, and the map above is updated in the same change.
2. **Only the owner writes.** Other modules call the owner's `pub` functions. Passing `&mut Transaction` is fine inside the monolith.
3. **Cross-module reads go through owner functions.** Exceptions: the identity views for display names, and the couplings already in the inventory. A new direct read of another module's table must be justified in the change and added to the inventory.
4. **No new cross-domain foreign keys, triggers or database functions without a decision-log entry.** Within a domain they are encouraged. Across domains, store `workspace_id` plus the target's ID and validate it by calling the owner under the workspace lock.
5. **Shared infrastructure stays domain-free.** `error.rs`, `state.rs`, `workspaces/` and `auth/` must not import a business domain. `routes.rs` is the composition root: a domain adds its routes with one `merge` line and its own database error mapper to `routes::DOMAIN_CODES`.
6. **Identity is resolved once per request.** Domains receive the live `UserRow`, scope and grants from `auth`/`workspaces` and do not query permission columns themselves.
7. **Side effects that can be asynchronous go through an outbox** written in the same transaction as the change: notifications, provider sends, catalogue refresh, AI agent work. Do not call another domain's write path for them. This is the roadmap's P2 foundation.
8. **Activity and history.** Redacted activity is written only through `records::audit::append`. Each new domain keeps its own detailed history table and never stores message bodies, recipient addresses, credentials or tokens.
9. **New large features are separately owned modules** with their own tables, routes, error codes and frontend client file:
   - `agreements/` (cross-company deal agreements);
   - `integrations/`, `inbox/`, `notifications/` (messaging and providers);
   - `publications/`, `catalogue/`, `enquiries/` (public website);
   - `lead_agents/` (AI lead agents).

   They do not add collections to `crm_records`, do not add projections to `GET records`, and do not take foreign keys into `crm_records` or `crm_deals`. They keep IDs plus frozen snapshots where evidence matters.

10. **Stable API surface.**
    - Private CRM paths stay under `/api/crm/workspaces/{ws}/<domain>/...`.
    - Public and guest surfaces get their own prefixes (for example `/api/public/...` or `/api/agreements/links/...`) so a gateway can route them separately, and never use CRM cookies.
    - Frontend code reaches the API only through `src/services/crm/`, one file per domain.
11. **Cross-tenant features never read another workspace's private tables.** Agreements, the public catalogue and enquiry routing use their own platform-level tables and approved projections.
12. **Automated check.** `npm run check:boundaries` (`scripts/check-boundaries.mjs`) scans `services/crm-api/src` for `crm_*` names outside comments and fails when:
    - a name has no owner in `scripts/boundaries.json` (add the owner with the migration, rule 1);
    - a module uses another module's table, view, function or constraint without an allowlist entry (`allowed`, one entry per module and name, each citing its coupling);
    - an allowlist entry is no longer used (delete it, so the list only shrinks);
    - `auth/`, `workspaces/`, `error.rs`, `state.rs` or `config.rs` names a business-domain module path (rule 5).

    The identity views are published to every module (rule 3) and `sample/` is unrestricted (C12). A new allowlist entry must be justified in the change and added to the inventory above. Run it with the standard checks.

## Likely extraction candidates, in order

1. **Integrations worker (messaging, providers, webhooks).** First a second binary in the same crate, sharing the database through the outbox and job tables; later a separate deployable if provider load or isolation requires it. Trigger: the first live provider (P2/P3).
2. **Public catalogue and enquiry intake.** `publications/` (private revisions and approval) stays in the CRM API. The catalogue read side and intake endpoint are built on their own tables, filled from the outbox, so they can move behind `/api/public` into a separate process with a restricted database role or replica. Trigger: website launch (P6/P7), or public traffic or exposure.
3. **Cross-company agreements.** Own module and tables from day one, with guest links and an evidence store. Extract when legal, evidence or retention requirements call for separate keys or storage.
4. **AI lead agents.** Asynchronous consumers of outbox events that create leads through a CRM command and never write to the database directly. A separate process from the start if they call external models.
5. **Identity and tenancy (auth, workspaces, team).** Only if SSO, customer accounts or mobile clients need a dedicated identity service. Needs C2, C3, C5, C6 and C8 resolved first.

Core CRM (records, assignments, imports and finance) stays together. Splitting it would cost the most and gain the least.

## Owner decisions (2026-10-15)

- **Own PostgreSQL schema for new large modules.** Agreements, messaging/integrations, public catalogue/enquiries and lead agents each get their own schema from their first migration, in the same database. Existing tables stay where they are.
- **Automated boundary check.** Rule 12 becomes a small Node script (no new dependency, within 150 lines) run with the standard checks, with an allowlist matching the coupling inventory. Done 2026-10-15: `npm run check:boundaries`.
- **Hosting.** Host in the UAE or a nearby region for data-protection reasons. Start with one API instance, managed PostgreSQL with automatic backups and the frontend on a CDN. Year-one company count, public traffic and acceptable downtime are set before launch and become the phase 3 split triggers.
