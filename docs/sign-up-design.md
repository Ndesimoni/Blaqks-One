# Public sign-up design

Status: design review (senior architect and product designer), 2026-10-16. Not built. Owner rules are in [Product decisions → Sign-up](product-decisions.md#sign-up-decided-2026-10-15-planned). This is a **sensitive** change (accounts, sessions, Admin creation), so it also needs a security review before building, under the [proportionate process](development-agents.md#proportionate-process-owner-decision-2026-10-14). Evidence comes from `feature/connected-crm` after commit 8e5004c, including the uncommitted language foundation (migration 0021).

## Key choices

| Topic                   | Decision                                                                                                                                                                                                                                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Where sign-up runs      | Only in **local development** until an email provider and a bot check are configured. `CRM_SIGNUP=off` (default), `local` or `live`. `live` refuses to start until packet S8 adds the adapters, so a hosted build cannot offer sign-up by mistake.                                                                                   |
| Code delivery           | A provider-neutral delivery interface writes every message to an outbox in the same transaction. In `local` mode a **dev outbox** "delivers" the message by printing it to the API terminal. No API response ever contains a code, even in local mode.                                                                               |
| Bot protection          | A provider-neutral bot-check interface. **Cloudflare Turnstile** is the suggested provider (it fits the planned Cloudflare hosting, see [Tech stack](tech-stack.md)). A local bypass works only in `local` mode. A failed or unavailable check fails closed.                                                                         |
| When the account exists | The account is created when the **email code is verified** (step 3), and the person is signed in then. Firm or profile details (step 4) are an ordinary signed-in update, so a person who leaves at step 4 still has a working account and sees the setup step at their next sign-in.                                                |
| Enumeration             | `start` and `resend` always return the same 202 response, with the same timing (Argon2 always runs). An email already in use gets a **decoy request**: no code is sent, and the mailbox gets an "you already have an account" notice. "Account exists" is revealed only after a correct code proves the person controls the mailbox. |
| Ownership               | A new `signup/` module owns the pending requests and their outbox. `auth/` keeps identity, sessions, consents and limits. `workspaces/` (tenancy) owns the new **company profile**, which holds the account type and the member limit. `team/` enforces the limit and runs the type switch.                                          |
| One model               | Both account types create a company (workspace) with the person as its Admin (`role='admin'`, exactly as for an invited Admin). Individual means `account_type='individual'` with `member_limit=1`. Switching changes two columns and never moves data.                                                                              |

## 1. User journeys

**Brokerage firm:** open **Create an account** from the sign-in page → choose **Brokerage firm** → enter name, email, mobile and password, and accept the terms → enter the 6-digit code → the account is created and signed in → company name and emirate → Dashboard with the get-started checklist, including **Invite your team**.

**Individual agent:** the same journey, choosing **Individual agent**. Step 4 asks only for a display name, prefilled with their own name, and can be skipped. The workspace has no Team features (see section 6).

| Case                                                                                                   | Behaviour                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email already has an account (active, suspended, pending invitation, cancelled invitation or archived) | The screens are identical. No code arrives, because the decoy request accepts no code. The mailbox gets a notice: sign in or ask for a password reset; for a pending invitation, "use the invitation link from your Admin"; for an archived address, "this email can't be used for a new account". |
| Wrong code                                                                                             | Error under the field: "That code is incorrect or has expired." After 5 wrong codes, that code is locked: "Too many incorrect attempts. Request a new code."                                                                                                                                       |
| Code expired (15 minutes)                                                                              | Same uniform error; **Resend code** issues a new code and invalidates the old one.                                                                                                                                                                                                                 |
| Resend                                                                                                 | Available after 60 seconds, with a visible countdown. At most 5 sends per request; after that, "Start again".                                                                                                                                                                                      |
| Typo in the email                                                                                      | **Use a different email** returns to step 2 with every field kept. The next submission starts a new request, and the old one expires on its own.                                                                                                                                                   |
| Page reload or the person leaves for their mail app                                                    | The tab keeps `{requestId, maskedEmail, accountType, expiresAt}` in `sessionStorage` (inside try/catch; never the password or code), so step 3 can resume. Without it, the person starts again at step 2.                                                                                          |
| Lost response on verify                                                                                | The client calls `GET /auth/session`. If a session exists, it continues to step 4. If not, a retry returns `invalid_code` (the request was consumed), so it shows "Your account may already be ready. Try signing in."                                                                             |
| Two tabs, or two people using the same email                                                           | Several pending requests may exist; only the mailbox owner can verify one. Verification takes a per-email advisory lock and relies on the `crm_users.email` unique index, so exactly one account is created. The other request gets 409 `account_exists`, but only after a correct code.           |
| Verify races a Super Admin invitation for the same email                                               | The unique index decides. The loser gets 409 (`account_exists` for sign-up, the existing duplicate error for the invitation).                                                                                                                                                                      |
| Already signed in                                                                                      | `/sign-up` shows "You're signed in as {email}. Sign out to create another account.", as the invitation page does.                                                                                                                                                                                  |
| Sign-up off                                                                                            | `/sign-up` shows "Sign-up isn't open yet" with **Go to sign in**, and the sign-in page shows no link.                                                                                                                                                                                              |
| Bot check blocked (for example by an ad blocker) or failing                                            | "We couldn't confirm you're human. Allow the check and try again." The form keeps its values. There is no bypass outside local mode.                                                                                                                                                               |
| Rate limited                                                                                           | Page alert with a translated retry message. The form keeps its values.                                                                                                                                                                                                                             |
| Leaving at step 4                                                                                      | A firm sees the setup step at its next sign-in, before the workspace. An individual may choose **Skip for now** (the display name falls back to their own name).                                                                                                                                   |

## 2. Screens

**Shell.** Reuse the connected sign-in layout (`sign-in-page` and `sign-in-shell`). At **1280px** there are two columns: the story panel (Blaqks One brand mark, one headline, three short benefit lines) and the form column with a reading width of at most 440px. At **390px** there is one column: the story shrinks to a brand row, with 16px gutters, no horizontal scroll and no sticky footer that could cover inputs or errors. Primary buttons are full width and 48px high. **Back** is a text button at the inline start, with a chevron mirrored in right-to-left layouts (`.u-mirror-rtl`). The theme switch stays in the corner.

**Progress.** "Step {step} of 4 · {title}" with four thin segments. Do **not** reuse `FormStepper`: its text is hard-coded English, and sign-up steps cannot be jumped between. On every step change, focus moves to the step heading (`tabIndex=-1`) and the progress text is announced (`aria-live="polite"`).

**Premium polish** ([standards](design-standards.md#premium-polish-for-new-work-owner-2026-10-16)), with the current tokens only:

- hierarchy through type and space: a 28/32px title, a 15px supporting line and 13px captions;
- hairline borders with a soft shadow on selected cards, and no nested panels;
- step changes fade and shift 8px along the inline axis over 160ms (the direction mirrors in right-to-left layouts), and nothing moves under reduced motion;
- skeletons in place while the status loads.

Every label, hint, error and button comes from the translation catalogues listed below.

## 3. Ownership and data model

| Module                                                                            | Owns (new)                                                                                                                                                                                                                                 | Calls                                                                          |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `auth/`                                                                           | `crm_users.email_verified_at`, `crm_account_consents`, the `signed_up` account event, `crm_login_limits.window_seconds`; new `auth::accounts::{create_admin, email_in_use}`, `auth::consents::record` and `auth::throttle::consume_window` | Nothing new (stays domain-free)                                                |
| `workspaces/`                                                                     | `crm_company_profiles` and `crm_company_events`; `workspaces::company::{create, get, seat_limit, set_type, update_details}`; `GET`/`PUT /workspaces/{ws}/company`                                                                          | Nothing new (stays domain-free)                                                |
| `team/`                                                                           | No tables. The seat check in invite, renew, activate and restore, plus the type-switch preview and commit                                                                                                                                  | `workspaces::company`, `auth::sessions`                                        |
| `signup/` (new, [rule 9](service-boundaries.md#boundary-rules-apply-from-now-on)) | `crm_signup_requests`, `crm_signup_outbox`; routes under `/api/crm/signup`; the delivery and bot-check interfaces                                                                                                                          | `auth`, `workspaces`, `sample::marker` (the existing local-development marker) |

`signup/` is a leaf: nothing imports it. Its tables keep the `crm_` prefix in the public schema, so `npm run check:boundaries` covers them without changes. The owner's own-schema decision names only agreements, messaging, the catalogue and lead agents, and sign-up belongs with identity if a split ever happens. Add the owners to `scripts/boundaries.json` and the domain map in the same change. The company profile has no foreign key to `crm_workspaces` (rule 4, following the `crm_account_events` precedent). Every workspace-creation path (bootstrap CLI, Admin invitation, sign-up) calls `workspaces::company::create` in the same transaction, and an API test asserts that every workspace has a profile.

**Migration A (owner: auth).**

- `crm_users.email_verified_at TIMESTAMPTZ NULL`. It is set at sign-up; invited and existing accounts stay NULL.
- `crm_account_consents(id, user_id, document IN ('terms','privacy'), version, accepted_at)`, with an immutable trigger.
- `signed_up` is added to the `crm_account_events` action check.
- `crm_login_limits.window_seconds INTEGER NOT NULL DEFAULT 900`. The clean-up becomes per row, so existing 15-minute limits behave exactly as before.

**Migration B (owner: workspaces).**

- `crm_company_profiles(workspace_id TEXT PRIMARY KEY, account_type TEXT CHECK IN ('brokerage','individual'), member_limit INTEGER NULL CHECK (member_limit >= 1), CHECK (account_type <> 'individual' OR member_limit = 1), display_name TEXT NULL CHECK (length 1–120), emirate TEXT NULL CHECK IN ('abu-dhabi','dubai','sharjah','ajman','umm-al-quwain','ras-al-khaimah','fujairah'), origin TEXT CHECK IN ('existing','operator','signup'), setup_completed_at, version BIGINT, created_at, updated_at)`.
  - Backfill every existing workspace as `brokerage`, with `member_limit NULL` (no limit while plans are free) and origin `existing`.
  - The organisation and Super Admin workspaces stay brokerage, and their type cannot be switched.
- `crm_company_events(id, workspace_id, actor_id, action IN ('created','details_updated','type_changed'), from_type, to_type, created_at)`, immutable, with no names or values.
- The workspace directory shows `COALESCE(display_name, owner name)`.

**Migration C (owner: signup).**

- `crm_signup_requests(id UUID PK, email (lowercase, ≤254), existing_account BOOLEAN, account_type, name, phone, password_hash ('' for decoys), language, terms_version, privacy_version, consented_at, code_hash, code_expires_at, code_attempts, sends, last_sent_at, created_at, expires_at DEFAULT now()+24h)`.
  - Indexes on `email` and on `expires_at`.
  - `email` is **not** unique: a squatter must never block the real owner.
  - `code_hash` is the SHA-256 of `request_id:code`.
- `crm_signup_outbox(id, request_id REFERENCES crm_signup_requests ON DELETE CASCADE, kind IN ('code','existing_account','invitation_pending','email_unavailable'), code TEXT NULL, channel, created_at, delivered_at)`.

**Clean-up.** Every `start`, `resend` and `verify` call first deletes expired requests (a bounded `DELETE`, as sign-in already does for expired sessions), and outbox rows cascade. A successful verify deletes its own request and every other pending request for that email in the same transaction, so no password hash outlives the request. Consent evidence then lives in `crm_account_consents`.

## 4. API

The routes are under `/api/crm/signup`, so the session cookie (`Path=/api/crm`) can be set at verify and a gateway can route or limit the prefix separately. All share these rules:

- a 16 KiB body limit and `deny_unknown_fields`;
- the exact Origin check, and no CSRF (there is no session yet);
- `Cache-Control: no-store`;
- the `{message, code}` error shape;
- 404 `signup_disabled` from every route except `status` when the mode is `off`.

## 5. Code delivery and bot protection

**Delivery.**

- Mode: `signup::delivery::Delivery` is chosen once at startup from configuration. `DevOutbox` exists now; `Provider` arrives in packet S8.
- Writing the message: `start` and `resend` write the message row (`kind`, a fresh 6-digit code from `OsRng`, the request id) into `crm_signup_outbox` in their own transaction ([rule 7](service-boundaries.md#boundary-rules-apply-from-now-on)). The address and language are read from the request row, so the outbox holds no address.
- Local delivery: after commit, `DevOutbox` prints one line to the API's standard error, for example `[dev-outbox] sign-up code 482913 for s•••@example.test, expires 14:20`, and marks the row delivered. It keeps the code in the row so the API and browser tests can read it through the disposable database helper (`query()` in `tests/api/helpers.mjs`).
- Provider delivery: the adapter later drains the same rows through the planned outbox worker, sends the localised email from a Blaqks One sending domain, and clears `code` once the provider accepts the message.
- Startup guard: `local` mode needs `CRM_ALLOW_INSECURE_LOCAL=true` (a loopback HTTP origin and bind) **and** the `crm_environment` local-development marker; otherwise the API refuses to start. `live` mode needs a provider and a Turnstile secret, and refuses to start until packet S8 exists.
- Truthful copy: the interface says "sent" only in `live` mode. Local mode says no email was sent.
- **Owner decision:** live delivery needs the **business mail system** decision (roadmap §17), narrowed to transactional sending: which provider sends Blaqks One codes and notices, and from which domain.

**Bot check.** The interface is `signup::bot::verify(token, action, client) -> Pass | Fail | Unavailable`, with actions `signup_start` and `signup_resend`.

- `LocalBypass` accepts only the literal token `local-development`, and only in `local` mode.
- `Turnstile` (packet S8, which adds `reqwest` with rustls, as the Calendar companion already uses) posts the secret, the token and the optional client key to Siteverify. It checks `success`, `action`, `hostname` and a token age of at most 300 seconds, and fails closed with 503 when Cloudflare cannot be reached.
- The frontend `BotCheck` component shows a muted "Bot check skipped in local development" line in local mode. In live mode it loads `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` once and renders the managed widget, in the active theme and language. It resets the widget after every submission, because tokens are single-use.
- When hosting adds a Content Security Policy, allow that origin for scripts and frames.
- Signing in may use the same interface later (tech-stack plan).

**Switch flow** (My profile → Account type, owner Admin only).

- **Individual → Brokerage.** One confirmation: "Your records stay exactly as they are. Team & access becomes available." This sets `brokerage` and `member_limit NULL`, and writes a `type_changed` event.
- **Brokerage → Individual.** A review dialog loads the preview and lists active members, pending invitations and suspended accounts.
  - Blocked while any other member is active: "Suspend or remove your other active members first." No switch button is shown.
  - Otherwise the switch commits with the fingerprint, and live pending invitations are **cancelled in the same transaction** (the review lists them).
  - Suspended accounts stay suspended and cannot be restored while the company is individual.
  - A teammate added or changed during the review returns 409 `review_changed`, and the review reloads.

## 7. Out of scope, with boundaries for later

- **Billing and plans.** All plans are free. `member_limit` is the hook for future plan limits; the platform dashboard sets it later.
- **Licence capture and verification.** A later `verification/` module owns licence numbers, the issuing authority and verification levels. Cross-company agreements and public listing approval share it. Sign-up only shows the caption.
- **Joining a firm and record transfer.** Today one email is exactly one account in one workspace (`crm_users.email` is unique, and `crm_staff_membership` holds a single owner). So a firm cannot invite an existing individual's email, and the current error is the generic 409 "That record ID is already in use." The later feature needs a separate identity and membership model (one sign-in, several memberships, a workspace switcher). Record transfer then belongs in its own `transfers/` module: it copies records with the firm Admin's acceptance, logs every step and never merges anything automatically.
- **Delivery and verification by providers.** This covers the email provider adapter, phone verification by SMS or WhatsApp (needed for the agreements' Basic level), password recovery, MFA, self-service account closure and the Super Admin platform dashboard.

## 10. Current code that blocks or complicates sign-up

- **Super Admin reach:** `workspaces::ensure_access` and the workspace directory open every workspace to the Super Admin (decision 2).
- **One email, one workspace:** `crm_users.email` is unique and `crm_staff_membership` allows one owner, so joining a firm needs a new membership model. Inviting an existing email fails with the misleading generic 409.
- **Workspaces have no name:** the directory shows the owner's name, hence the company profile.
- **Fixed limit windows:** `auth/throttle.rs` uses one 15-minute window and a global clean-up, and has no trusted client key, hence S1.
- **No HTTP client:** `services/crm-api` has none, so Turnstile and email adapters add `reqwest` in S8.
- **Approval-only finance:** payments and expenses always start pending, hence S7.
- **No recovery and no terms:** password recovery and legal texts do not exist, and invitation activation records no consent.
- **Frontend:** the sign-in brand is hard-coded, `FormStepper` text is hard-coded English, `src/styles/auth.css` (399 lines) is oversized and physical, and `ServerSession.jsx` routes by pathname (add `/sign-up` beside `/activate-invitation`).
- **Uncommitted work:** auth, the API test runner and migration 0021 are being edited now, so migrations A to C take the next free numbers when built.
