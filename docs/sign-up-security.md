# Sign-up security review

Security review of owner-approved public self sign-up ([Product decisions](product-decisions.md#sign-up-decided-2026-10-15-planned)), written 2026-10-16 against the `feature/connected-crm` working tree. Read it with [Sign-up design](sign-up-design.md). At review time, nothing here was implemented. Every requirement must pass before sign-up is enabled anywhere, including local development. Module names marked "proposed" are suggestions for the architect.

**Implementation update (2026-10-19):** the findings below record the pre-implementation review. S1 auth groundwork, S2 company profiles, S3 seat enforcement, the local-only S4 sign-up API and the visible three-step sign-up flow are implemented. Every verified account now creates a company workspace on the Free plan with three total seats. Provider delivery, hosted bot checks, trusted client keys, recovery, MFA and billing remain later packets. See the implementation notes in [Sign-up design](sign-up-design.md).

## What changes

Until now every Admin was created by the Super Admin, so Admin was a trusted role. With self sign-up, **anyone with a mailbox becomes an Admin in minutes**. Every Admin-only capability, including invitations, becomes reachable by untrusted users. The new unauthenticated surface is: start (details, password, consent), resend code and verify code. After verification there is an authenticated finish step for firm or profile details.

| Threat                        | Attack path                                                                                           | Controls  |
| ----------------------------- | ----------------------------------------------------------------------------------------------------- | --------- |
| Account enumeration           | Different response, timing or side effect for a known email at start, resend, verify, login or invite | E1–E5     |
| Code guessing                 | Brute-forcing a 6-digit code, parallel guesses, or using resend to reset counters                     | C1–C8     |
| Email bombing, mass companies | Scripted starts against victims' addresses, or throwaway mailboxes creating companies                 | B1–B6     |
| CPU exhaustion                | One Argon2 hash per request                                                                           | P1–P3     |
| Seat or identity hijack       | Sign-up claiming a pending invitation (another company's seat) or reviving an archived identity       | U1–U5     |
| Privilege escalation          | Role, workspace or limit fields in the body; reading other companies                                  | A1–A2     |
| Team-limit bypass             | Exceeding a company's seat cap through invitation, activation, renewal or member restoration          | A3–A5     |
| Login CSRF, session fixation  | A hostile site completing a sign-up into an attacker-controlled account                               | S1–S4     |
| Secret or PII leakage         | Codes, passwords, emails or mobiles in logs, activity or the outbox                                   | L1–L3, D3 |
| Production bypass             | The development outbox or bot bypass reachable on a hosted server                                     | G1–G4     |
| Public exposure               | Availability checks or company pages on the public website                                            | W1–W2     |

### C. Email codes

### B. Abuse budgets and bot protection

Starting limits, to be tuned before hosting: sends per client IP 10/hour. Sends per email budget key (lower case, `+tag` removed, Gmail dots removed) 3/hour and 10/day. Global sends 300/hour. Wrong codes per IP 30/hour. Companies per IP 3/day. Global companies 30/hour and 200/day. Existing-account notices per email 1/hour.
